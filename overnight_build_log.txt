ARCHITECTURE DECISIONS
-----------------------
- Wire protocol: custom UDP protocol (not raw RTP, not full Sunshine/Moonlight
  integration) — 3 channels (control/video/input), fragmented Annex-B H264
  frames, documented in shared-protocol/PROTOCOL.md as the single source of
  truth both implementations coded against independently.
- PC host: C# / .NET 8 console app, ffmpeg subprocess for capture+encode,
  hand-rolled UDP networking + SendInput P/Invoke for input injection.
- iOS client: native Swift/UIKit/SwiftUI, scene-role-based external display
  routing (UIWindowSceneSessionRoleExternalDisplay), VideoToolbox decode,
  AVSampleBufferDisplayLayer render, Network.framework UDP.
- Multi-agent breakdown: PC-Host-Agent and iOS-Swift-Agent worked the two
  codebases in parallel against the shared protocol doc; coordinator
  (this session) owns protocol spec, scaffolding, integration, and review.

- Mock mode (`--mock`) verified end-to-end against `tests/mock_udp_receiver.py`:
  fragments arrive and reassemble correctly (~62fps over 8s).
- REAL capture path verified end-to-end on this machine's actual screen +
  GPU: ffmpeg launches, captures via ddagrab (DXGI Desktop Duplication),
  encodes, and streams real H264 over UDP. ffprobe confirmed the
  reassembled stream is valid decodable H264, 1920x1080, yuv420p,
  Constrained Baseline profile, 50/50 frames decoded.
- Real bug #1 found & fixed: NVENC does not actually work on this dev
  machine (RTX 5070 Ti, driver 595.95 vs ffmpeg 8.1.2's nvenc requiring
  driver >=610.00). EncoderProbe.cs detects this at startup and falls back
  to libx264 automatically. Capture itself (ddagrab/DXGI) stays GPU-side
  regardless — only the encode stage is affected.
- Real bug #2 found & fixed (the significant one): under `-tune
  zerolatency`, both libx264 and nvenc use slice-based threading that
  splits every picture — including IDR keyframes — into multiple slice NAL
  units all sharing the same nal_unit_type (17 slices/picture observed on
  this machine). The original "one VCL NAL = one frame" splitter therefore
  fragmented each real picture into ~17 bogus frames, inflating apparent
  frame rate ~17x and producing corrupt access units. Fixed by requesting
  Access Unit Delimiters from the encoder (-x264-params aud=1 / -aud 1) and
  rewriting AnnexBFrameSplitter.cs to treat AUD (NAL type 9) as the
  authoritative per-picture boundary, with the old heuristic kept only as a
  fallback for AUD-less streams. Verified via manual NAL analysis and a
  dedicated regression test.
- Spot-checked by coordinator: AnnexBFrameSplitter.cs and EncoderProbe.cs
  read in full — logic is sound, edge cases (first-NAL-is-AUD, pipe
  draining/deadlock avoidance) are handled correctly.

BOTH TRACKS — PROTOCOL BUG FOUND
------------------------------------------------------------------------
Both agents independently flagged the same error in PROTOCOL.md (written
by the coordinator before either agent started): Disconnect's `reason`
field was documented at offset 5, overlapping the 4-byte sessionId field
(bytes 4-7). Both implementations independently resolved it to offset 8,
and PROTOCOL.md has been corrected to match. This is the kind of doc bug
that would otherwise have caused a real interop mismatch invisible to
either side's unit tests (since each side would just be internally
consistent with its own, differently-wrong, interpretation).
